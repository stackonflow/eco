## 4.2 WasteRate model

Create or update a Mongoose model containing:
- Category.
- Rate per kilogram.
- Active/inactive status.
- Created and updated timestamps.

Validate rates and prevent conflicting active rate definitions for the same category.

Only administrators can create, edit, activate, or deactivate rates.

## 4.3 Waste submission form

Create a responsive form with:
- Waste category.
- Estimated quantity in kilograms.
- Pickup address.
- Preferred pickup date and time.
- Optional description.
- Optional image upload only if the existing infrastructure supports it safely.

Validate required fields, positive quantities, sensible limits, and valid future dates where applicable.

Display the current active rate and calculate:

`Estimated Value = Estimated Quantity (kg) × Current Rate per kg`

Clearly label the value as an estimate rather than a guaranteed payout.

The frontend may show a live estimate, but the backend must independently retrieve the active rate and calculate the authoritative value.

## 4.4 PickupRequest model

- Request status.
- Assigned collector reference, when assigned.
- Collection and verification timestamps, where applicable.
- Created and updated timestamps.

Use the existing user model and reference structure.

Historical requests must retain their original rate and estimated value if the current rate changes.

# 5. Phase 3 — Pickup Scheduling, Collection, Verification, Receipts, and Inventory

After Phase 2 is implemented, connect it to a complete collection workflow.

## 5.1 Pickup assignment and scheduling

Extend the existing request workflow to support:
- Pending.
- Accepted.
- Scheduled.
- Collected.
- Verified.
- Completed.
- Cancelled or rejected where appropriate.

Use valid state transitions and enforce them on the backend.

Administrators should be able to assign an authorized collector to a request and set or update its scheduled collection time.

Collectors should only be able to view and manage requests assigned to them, unless the existing permission model explicitly grants broader access.

Users should be able to view:
- Current request status.
- Scheduled collection date and time.
- Assigned collector information where appropriate.
- Status history or important updates.

Prevent unauthorized status changes and duplicate assignments.

## 5.2 Collector dashboard

Create a collector dashboard matching the existing EcoCycle design.

Include:
- Assigned pickups.
- Upcoming collections.
- Pending tasks.
- Pickup addresses.
- Waste categories and estimated quantities.
- Scheduled times.
- Current statuses.

Allow collectors to open a request, review its details, and update its status only through valid workflow transitions.

Provide clear empty, loading, success, and error states.

Do not allow collectors to modify waste rates or unrelated users' requests.

## 5.3 Actual weight and quality verification

After a collector marks a request as collected, allow authorized verification.

Record:
- Actual measured weight in kilograms.
- Material quality or condition.
- Approved final rate per kilogram.
- Verification notes.
- Collector identity.
- Verification timestamp.

Calculate:

`Final Payable Amount = Verified Weight (kg) × Approved Final Rate per kg`

The backend must validate and calculate the final amount.

Do not trust a final amount supplied by the frontend.

Keep estimated values separate from verified values. Preserve the original estimate and rate snapshot.

Only authorized collectors assigned to the request or authorized administrators should be able to perform verification.

Prevent unauthorized changes to completed verification records. If corrections are necessary, record them through an explicit authorized correction process.

## 5.4 Digital receipts

Generate a unique digital receipt once the waste has been successfully verified.

Each receipt should contain:
- Unique receipt number.
- Pickup request ID.
- User details.
- Waste category.
- Estimated quantity and value.
- Actual verified weight.
- Final approved rate per kilogram.
- Final payable amount.
- Collection date.
- Verification date.
- Payment status.

Store receipts in MongoDB or generate them from immutable, persisted verification data with a stable unique receipt identifier.

Users should be able to view their own receipts and print or download them.

Administrators should be able to view receipts for authorized operational purposes.

Do not generate multiple inconsistent receipts for the same completed verification.

## 5.5 Inventory batches

After successful verification, create an inventory batch representing the collected waste.

Each batch should include:
- Unique batch ID.
- Waste category.
- Verified quantity.
- Available quantity.
- Reserved quantity, initially zero.
- Quality classification.
- Source pickup request.
- Collection date.
- Processing status.
- Storage location if applicable.
- Created and updated timestamps.

Prevent duplicate inventory creation when the same pickup request is retried or processed more than once.

Ensure that the batch quantity is consistent with the verified collection record.

## 5.6 Inventory tracking and QR codes

Generate a unique QR code for each inventory batch.

The QR code should identify the batch and link to a suitable batch-detail route.

Apply access controls to sensitive batch information. Public QR views, if supported, must not reveal private user information or internal financial details.

Create an inventory management page for administrators showing:
- Batch ID.
- Waste category.
- Verified quantity.
- Available quantity.
- Reserved quantity.
- Quality.
- Processing status.
- Collection date.

Track inventory status changes and prevent quantities from becoming negative.

Do not implement recycler sales or inventory reservation for actual sales in this phase; those belong to Phase 4.

## 5.7 Processing status

- Suitable recycling facilities for plastic, paper, cardboard, metal, and glass.

# 6. Database and Financial Integrity

Create or update Mongoose models as required for:
- WasteRate.
- PickupRequest.
- Receipt.
- InventoryBatch.
- Any necessary status-history or inventory-transaction model.

Reuse the existing User model and authentication architecture.

Use schema validation, timestamps, appropriate indexes, and unique identifiers.

Enforce these invariants:
- Users cannot access another user's private requests or receipts.
- Collectors cannot update requests they are not authorized to manage.
- Only administrators can manage rates and assign collectors.
- The backend calculates all estimates and final amounts.
- The same pickup cannot create duplicate receipts or inventory batches.
- Verified quantities cannot produce negative inventory.
- Historical estimates remain unchanged when current rates change.
- Invalid state transitions are rejected.
- Completed financial and verification records cannot be silently rewritten.

Use MongoDB transactions when supported by the configured deployment and required by the operation. If transactions are unavailable, use appropriate atomic updates and idempotency protections.
