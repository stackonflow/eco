# 1. Project Overview

EcoCycle is a waste-management and recycling platform designed to connect households, waste collectors, recycling companies, and administrators.

The platform aims to transform recyclable waste into a potential source of income by managing waste submissions, estimated values, collections, material verification, inventory, recycling, sales, and payments.

The application uses the MERN stack:

- **Frontend:** React + Vite
- **Backend:** Node.js + Express.js
- **Database:** MongoDB + Mongoose
- **Authentication:** JWT + bcrypt
- **Styling:** CSS
- **API communication:** REST APIs
- **Validation:** Existing validation framework, or an appropriate library if needed

Use the existing architecture and dependencies wherever possible. Do not introduce Java, Spring Boot, or MySQL.

# 4. Phase Two — Waste Submissions and Rate Management

Once the existing application starts reliably and the UI redesign is complete, implement Phase 2.

Inspect the current codebase first. Reuse existing models, routes, components, and utilities when appropriate.

Do not create duplicate implementations if any of these features already exist.

## 4.1 Waste categories

Support the following categories:

- Plastic
- Paper
- Cardboard
- Metal
- Glass
- E-waste
- Organic waste

Use a consistent set of category identifiers across the frontend, backend, and database.

## 4.2 WasteRate model

Create or update a Mongoose model containing:

- Waste category.
- Rate per kilogram.
- Active/inactive status.
- Created timestamp.
- Updated timestamp.

Enforce appropriate validation and prevent duplicate active rate definitions for the same category.

Only authorized administrators may create, edit, activate, or deactivate rates.

Use the existing authentication and role system. Do not create a competing authorization mechanism.

## 4.3 Waste submission form

Create a polished, responsive page that allows authenticated users to submit waste collection requests.

Include:

- Waste category.
- Estimated quantity in kilograms.
- Pickup address.
- Preferred pickup date and time.
- Optional description.
- Optional image upload only if the existing infrastructure supports it safely.

Validate required fields, positive quantities, reasonable limits, and valid pickup dates.

Show the current active rate for the selected category.

Calculate:

`Estimated Value = Estimated Quantity (kg) × Current Rate per kg`

Display the estimated rate and total clearly. Label the total as an estimate, not a guaranteed payout.

Update the estimate when the selected category, quantity, or active rate changes.

## 4.4 PickupRequest model

Create or update a Mongoose model containing:

- User reference.
- Waste category.
- Estimated quantity.
- Pickup address.
- Preferred date and time.
- Optional description.
- Rate snapshot used for the estimate.
- Estimated value.
- Request status.
- Created timestamp.
- Updated timestamp.

Use the existing user model and reference structure.

The backend must retrieve the applicable active rate from MongoDB and calculate the estimated value itself.

Never trust a price, estimated total, user ID, or role supplied by the frontend.

Store the rate and estimated value used when the request is created. Historical requests must retain their original rate snapshot even if the administrator later changes the current rate.

Use a sensible initial status, such as `pending`.

Do not implement the full collector scheduling or physical verification workflow in this phase.

## 4.5 Backend APIs

Implement or extend APIs for:

- Listing active waste rates.
- Creating a waste submission.
- Listing the authenticated user's own submissions.
- Retrieving an individual request with ownership checks.
- Admin listing of all waste requests.
- Admin creation of waste rates.
- Admin updating of waste rates.
- Admin activating and deactivating rates.

Follow the existing route naming conventions where reasonable.

Use:

- Input validation.
- Authentication middleware.
- Role-based authorization.
- Consistent response formats.
- Appropriate HTTP status codes.
- Centralized error handling.
- Ownership checks.

Users must only access their own requests. Administrators may view and manage requests across users.

Ensure that unauthorized requests cannot change rates or access private records.

## 4.6 User-facing pages

Implement or refine:

### Submit Waste

A form for submitting recyclable waste with live estimate calculation, validation, and helpful feedback.

### My Waste Requests

A page showing the authenticated user's actual saved requests.

Display:

- Estimated quantity.
- Rate per kilogram.
- Estimated value.
- Submission date.
- Request status.

Include loading states, empty states, and error handling.

Users should be able to refresh the page without losing access to previously submitted requests.

## 4.7 Admin pages

Implement or refine:

### Waste Rate Management

Administrators can:

- View current rates.
- Create rates.
- Edit rates.
- Activate or deactivate rates.

### Waste Request Management

Administrators can:

- View all requests.
- Search or filter requests.
- View request details.
- Review submission dates, quantities, estimates, and statuses.

Use readable tables and simple forms where appropriate. Do not turn every row or field into a large decorative card.

All administrative permissions must be enforced on the backend.

## 4.8 Database persistence

Persist all waste rates and requests in MongoDB.

Verify that:

- New requests are saved to MongoDB.
- Users can retrieve their own requests after refreshing.
- Rates are loaded from the database.
- Rate changes affect new estimates.
- Historical requests retain their original rate and estimated value.
- Inactive rates cannot be used for new requests.
- Unauthorized users cannot access another user's data.
- Non-admin users cannot modify rates.

Do not substitute hardcoded arrays or local component state for required database operations.
